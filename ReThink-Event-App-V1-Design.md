## Problem Statement

ReThink is a learning community for PMs and builders. Participation drops when
visibility disappears: activity is scattered across WhatsApp, LinkedIn, an LMS
nobody opens, and personal calendars. Founder-flown city meetups (Bangalore,
Pune, Delhi, Hyderabad, Nov–Dec 2025) proved demand but don't scale, because
every event needs a founder (Unnati, Atharv, Shravan) to arrange it.

The work to date is three documents at three altitudes:
- **Primary doc (Rethink team)** — the vision/why. Targets the visibility problem.
- **Krishna's doc** — strategy. Targets relevance/trust (match scoring, host
  credibility, participation proof).
- **Aditya's doc** — mechanisms. A PRD+tech spec targeting agency (trusted-host
  publishing) + visibility (feed, public share pages, reminders), and explicitly
  deferring relevance.

This session's job: confirm the direction is right and lay out a realistic,
sexy-yet-minimal V1 go-to-market.

## Demand Evidence

Confirmed by the user: the Nov–Dec 2025 founder-flown city meetups proved people
show up. Demand is real. V1 does NOT need to manufacture demand. Its job is to
scale supply (events that happen without founders) and visibility.

## Status Quo

Events today run on WhatsApp groups, LinkedIn/Instagram posts, an LMS, and
personal calendars. Every event requires a founder to personally arrange venue,
calls, and logistics; city leads help out of friendship, not structure. There is
no software product yet — V0 is a proposal, not built (confirmed). Clean slate.

## Target User & Narrowest Wedge

Two sides:
- **Attendee** — a ReThink member who wants relevant sessions worth their time
  and proof they're participating.
- **Host** — a trusted community member who wants to run a session without a
  founder having to organize it for them.

Stated bottleneck ordering (user's call): **agency first, visibility second,
relevance later.** The narrowest wedge that breaks the first bottleneck:
a trusted member can create, publish, fill, and run an event solo, and that
event is a beautiful shareable link.

## Constraints

- **Sign-in-gated participation, open registration.** Anyone can discover an
  event via LinkedIn/Instagram, land on a public page, and join by signing up;
  you must be signed in to RSVP or host. No allowlist/whitelist gate. (Avoid the
  phrase "members-only" — it implies a gate that doesn't exist. This is a
  deliberate reversal of Aditya's whitelist-gated model — see Open Questions.)
- No payments in V1 (paid tickets are "much later").
- Not a chat platform, not a learning platform, not a job board, not premium
  networking (shared non-goals across all three docs).

## Premises

Confirmed with the user (premise 3 revised after pushback):

1. **Demand is proven.** V1 scales supply and visibility, not demand. ✅
2. **Agency is the spine.** Trusted-host publishing (first event reviewed, then
   instant) is the one non-negotiable. Without it, it's a prettier admin tool. ✅
3. **Relevance: keep the OUTCOME in V1, cut the ALGORITHM.** (Revised.) The user
   wants early members to feel "this is for me," and is right that the absence of
   felt relevance would make early adopters churn. The resolution: at 5–8 events,
   relevance is a **curation problem, not a computation problem**. A cold-start
   match algorithm is at its *weakest* exactly at launch (no history, few events),
   so it would give the earliest members the worst version of the thing they care
   about. Hand-curation + tags + stated goals + cohort social proof delivers
   better felt relevance at low volume, at ~5% of the build. The match *score*
   is deferred to V2; the trigger to build it is the day hand-curation can't keep
   up. ✅ (EUREKA — see below.)
4. **The public share page + ticket stub is the growth surface.** The one thing
   V1 must make genuinely sexy. ✅
5. **Custom-built is justified** only because the members-only trust layer + the
   cohort funnel is the actual product; generic discovery (Luma) is not the moat. ✅

EUREKA: Relevance at low volume is a curation problem, not a computation problem.
Building the match algorithm in V1 is premature optimization that also delivers
the worst version (cold start). Curate now; compute when curation breaks.

## Approaches Considered

### Approach A: Aditya-full (mechanism-heavy V1)
Ship the full PRD: trusted-host publishing, public pages + OG, ticket + QR
check-in, waitlist + atomic promotion, conflict warnings, online/offline meet-URL
gating, host broadcast + email fan-out, 24h reminders.
- Effort: L/XL. Risk: Med.
- Pro: Complete; nothing to retrofit. Pro: handles scale-day-one edge cases.
- Con: Solves problems you won't have yet (waitlists, conflicts, QR) for a
  community that has shipped zero events through software. Con: slowest GTM.

### Approach B: Krishna-relevance (trust/proof-heavy V1)
Lead with match scoring, host credibility grading, participation proof, the
structured Room taxonomy as enforced formats.
- Effort: L. Risk: High.
- Pro: Strong differentiation thesis; defensible long-term.
- Con: Builds the V3 brain before the V1 skeleton has a heartbeat. Con: match
  algorithm is weakest at cold start — worst possible first impression. Con:
  doesn't break the agency bottleneck, which is bottleneck #1.

### Approach C: Curated-minimal, agency-first (RECOMMENDED)
Trusted-host publishing + curated feed + public share page + ticket stub +
reminder + lite host run-tools + relevance-by-curation. Defer all heavy
machinery.
- Effort: M. Risk: Low.
- Pro: Breaks all three bottlenecks in the user's stated order. Pro: ships fast,
  has a real growth loop, gives early members genuine felt relevance. Pro:
  shortest path to a sexy GTM artifact.
- Con: Will need fast-follows (waitlist, match score) once volume arrives —
  but those triggers are obvious and the work is additive.

## Recommended Approach

**Approach C.** It matches the confirmed bottleneck ordering, ships the sexiest
artifact (shareable public page + ticket stub) first, and avoids building the
relevance/proof/scale machinery before there's volume to justify it.

### V1 build — final scope

**Spine (breaks agency + visibility):**
1. Open signup + email OTP login. Anon can view public event pages; sign in to
   RSVP or host.
2. **Trusted-host publishing**: member proposes → first event admin-reviewed →
   approval flips them to trusted → all future events publish instantly.
   - **Event lifecycle states** (explicit): `draft` → `pending_review` →
     `published` → `cancelled` / `taken_down`. Trusted hosts skip
     `pending_review` (publish on create). Only `published` events appear in the
     feed and on public pages.
   - **Host can edit and cancel** a published event. Cancel emails all RSVPs and
     marks the calendar entry cancelled. (Edit of time/venue also re-notifies.)
   - **Capacity**: events have an optional hard cap. At cap the event shows
     `FULL` and RSVP is blocked. (Waitlist/promotion is the deferred part, not
     the cap itself.)
   - **Auth/OTP edge cases** (resend, expiry, rate-limit) handled by the auth
     provider (Supabase Auth) — not custom code.
3. Curated feed: 3 sections (happening now / you're in / everything else) +
   tag and city filters. **Low-volume state**: at launch with <5 events, collapse
   empty sections and lead with "For you" — design for the near-empty feed, it's
   the common case for weeks.
4. Native RSVP + add-to-calendar (ICS / Google Calendar link).
5. Host run-view: attendee list + manual check-in toggle + **one broadcast
   message per event** (this replaces the WhatsApp group; one-way, not chat).
6. 24h reminder email.
7. Admin: approval queue, trust toggle, takedown. (No allowlist gate.)

**Relevance-by-curation (the V1 relevance outcome, no algorithm):**
8. Member states **goal + level** at signup (two dropdowns).
9. Event **tags** (beginner / interview-prep / AI-PM / build / resume). **City**
   is a separate field, a fixed **enum of the launch cities** (Bangalore, Pune,
   Delhi, Hyderabad), not free text — no city-admin system in V1.
10. "For you" row, assembled from three cheap signals (no algorithm):
    - **filter** on the member's goal + level against event tags;
    - **admin hand-pick**: a per-event `featured_for {goal, level, city}` flag an
      admin sets — this is the data model behind "curation," keep it this simple;
    - **cohort social proof**: "N from your cohort are going," where **cohort =
      members matching your goal + level + city**. Define it exactly this way so
      the query is buildable.

**Growth + delight (the wedge):**
11. Public read-only event page `/e/[id]` + **OG share card** + WhatsApp share.
    Treat the **dynamic per-event OG image route** (Next.js `ImageResponse`,
    font loading, the "sexy" bar from Premise 4) as a **first-class workstream
    with its own estimate**, not a footnote — it is the designated growth surface
    and can't be quick-and-dirty.
12. **Lite ticket stub** — screenshot-worthy confirmation with calendar + share,
    **no QR** in V1.
13. **Post-session feedback**: thumbs up / down + optional one-line text field
    (opens on tap). Feedback is attached to the **event** (not the host) and
    visible **only to admins and that event's host** — preserves the
    no-public-ratings principle from both docs. (User chose binary over the
    recommended 3-point scale.)

**Explicitly deferred to V2:** relevance *score*/match algorithm, participation
proof / badges / streaks, host grading rubric, structured Room taxonomy as
enforced formats, waitlist + atomic promotion, QR check-in, conflict warnings,
online/offline meet-URL gating, payments / paid tickets, threaded or two-way
broadcast.

## Open Questions

1. **Auth model reversal.** V1 assumes open signup, not Aditya's whitelist gate.
   Confirm with the team — is there any curation/trust reason the community must
   gate signup (vs. gating only participation)? Free vs. paid community tiering
   is parked for later.
2. **Feedback granularity.** User chose thumbs up/down. Flag for revisit: binary
   is blind to the "it was fine" middle, which is the most useful early
   curation signal. Consider 3-point in V1.1 if the binary proves too coarse.
3. **Subjective text in V1 vs V1.1.** Kept optional in V1 (one textarea); team
   had leaned toward deferring. Low stakes.
4. **Online vs offline events.** V1 leans offline-first (city meetups). Decide
   whether online events need any handling in V1 or go in the description field.

## Success Criteria

From the primary docs, adapted:
- % of published events created by **non-admin members** (agency broken).
- Time from create → live for a trusted host (target: minutes).
- RSVP → attendance conversion (target: > 50%); reminder email open rate.
- Anon visits to `/e/[id]` and login-from-event conversions (growth loop works).
- At least 2 hosts want to host again.
- Members report relevance + host credibility helped them decide.

## Distribution Plan

Web app (Next.js on Vercel, per Aditya's stack). Existing web deployment
pipeline covers distribution. The growth surface IS the distribution channel:
public event pages with OG cards shared to WhatsApp / LinkedIn / Instagram.

## Dependencies

- Stack per Aditya's tech guide: Next.js App Router + Supabase (Auth, Postgres +
  RLS, Storage) + a transactional email provider + an OG image route. Verify
  before committing — no migrations exist yet (greenfield), so the whole stack
  starts unvalidated.
- **RLS is the trickiest correctness surface.** Before coding, enumerate the
  **role × state visibility matrix** (anon / member / host / admin × draft /
  pending / published / cancelled / taken_down). "First event reviewed, then
  instant publish" plus who-can-see-what is easy to get subtly wrong in RLS.
- **Name the email provider and set up domain auth (SPF/DKIM) early.** Reminder
  and broadcast deliverability is on the critical path — success criteria track
  open rates, so a cold sending domain fails the metric before the product does.
- A small set of seed hosts/sessions for the validation run (below).

## The Assignment

Run the validation play before writing production code: ask ~30 members what
session they could confidently host. Pick 5. Curate them into a single page (can
be a manual page, not the app). Tag them. Share hand-picked recommendations with
10 members. Track RSVP, attendance, feedback, and repeat interest. If at least
8–10 members surface clear session ideas and RSVP→attendance clears 50%, the
agency + curation thesis is validated and V1 is de-risked before a line of app
code ships. This directly tests Premise 3 (curation beats algorithm at low
volume) in the real world.
